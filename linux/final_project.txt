
ОТЧЕТ О ВЫПОЛНЕНИИ ПРАКТИЧЕСКОЙ РАБОТЫ

Тема: Диагностика и восстановление работоспособности веб-сервера, настройка ротации логов и резервного копирования.

1. Постановка задачи

Веб-сайт (MediaWiki), развернутый на облачном сервере AWS EC2, перестал открываться по неизвестной причине. Необходимо подключиться к серверу, выявить причины сбоя, восстановить работу веб-приложения и оптимизировать систему хранения резервных копий и логов.

2. Ход выполнения работ и диагностика

1. Первичная проверка и подключение к серверу
	• Проведена визуальная проверка доступности ресурса в браузере по адресу http://3.75.84.224 — сайт не загружается.
	• Выполнено подключение к серверу по протоколу SSH: ssh -i ~/.ssh/ich.pem ec2-user@3.75.84.224.
	• Проверка статуса веб-сервера (sudo service httpd status) и попытка его перезапуска (sudo service httpd restart) не устранили проблему.
2. Устранение нехватки дискового пространства
	• В процессе диагностики обнаружена критическая системная ошибка No space left on device (на диске закончилось свободное место).
	• Командой df -h подтверждено 100% заполнение корневого раздела.
	• Выполнен поиск файлов размером более 100 МБ от корня файловой системы с правами суперпользователя: sudo find / -type f -size +100m.
	• Обнаружен разросшийся файл журнала access_log размером 7 ГБ, который был удален (sudo rm -rf /var/log/httpd/access_log) для освобождения места.
3. Исправление конфигурации веб-приложения
	• После очистки диска и перезапуска службы httpd сайт по-прежнему не открывался из-за ошибки в конфигурации MediaWiki (переменная $wgServer).
	• В директории сайта обнаружен поврежденный конфигурационный файл и его резервная копия LocalSettings.php (5).php. Файл скопирован в рабочую директорию /var/www/... под корректным именем LocalSettings.php.
	• С помощью текстового редактора nano в файле LocalSettings.php обновлено значение переменной $wgServer: прописан актуальный IP-адрес сервера (сбой произошел из-за отсутствия статического IP-адреса — после перезагрузки инстанса адрес изменился).
	• После перезапуска Apache (sudo service httpd restart) работоспособность веб-сайта была полностью восстановлена.
4. Аудит планировщика задач и настройка скрипта резервного копирования
	• Проверка директории логов (sudo ls -al /var/log/httpd) и списка задач планировщика (crontab -l) выявила некорректно настроенное задание с расписанием * * * * * (запуск каждую минуту), которое бесконтрольно создавало архивы и забивало диск.
	• Через crontab -e ошибочная задача отключена, старые ненужные архивы удалены.
	• Разработан и внедрен Bash-скрипт для корректного ежедневного архивирования логов с последующей очисткой исходной директории и удалением архивов старше 3 дней:

================================================================================

#!/bin/bash

# --- Блок настройки переменных ---
SOURS_DIR="/var/log/httpd"          # Директория с исходными логами веб-сервера Apache
ARH_DIR="/home/ec2-user/BACKUP"     # Папка для сохранения готовых резервных копий
MAX_BACKUP=3                        # Срок хранения старых архивов (в днях)

# Формируем текущую дату и время (формат: ГГГГММДД-ЧЧ:ММ:СС) для уникального имени файла
DATE=$(date '+%Y%m%d-%T')

# Создаем директорию для бэкапов, если она еще не существует (ключ -p игнорирует ошибку, если папка уже есть)
mkdir -p "$ARH_DIR"

# Задаем полный путь и имя будущего архива
ARH_NAME="$ARH_DIR/httpd_log_$DATE.tar.gz"

# --- Блок архивирования и очистки ---
# Упаковываем и сжимаем папку с логами в tar.gz архив
sudo tar -czf "$ARH_NAME" "$SOURS_DIR"

# Останавливаем веб-сервер, чтобы корректно очистить открытые файлы логов
sudo service httpd stop
# Удаляем все старые файлы логов из рабочей директории Apache
sudo rm -rf "$SOURS_DIR"/*
# Запускаем веб-сервер обратно (Apache автоматически создаст новые пустые файлы логов)
sudo service httpd start

# --- Блок ротации (удаления старых бэкапов) ---
# Ищем в папке бэкапов файлы с расширением .tar.gz старше 3 дней (-mtime +3) и удаляем их
find "$ARH_DIR" -type f -name "*.tar.gz" -mtime +"$MAX_BACKUP" -exec rm -rf {} \;

==================================================================================================

3. Выводы и рекомендации

• Ротация логов: Вместо самописных скриптов очистки журналов системному администратору рекомендуется настроить штатную утилиту ротации логов Linux через конфигурационный файл /etc/logrotate.d/httpd.
• Сетевая конфигурация: Для предотвращения подобных сбоев в будущем необходимо привязать к серверу постоянный (статический) IP-адрес (Elastic IP в AWS)
